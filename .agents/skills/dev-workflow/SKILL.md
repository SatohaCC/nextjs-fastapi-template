# 開発ワークフロー

## 着手から PR 提出まで

1. **親 Issue とサブ Issue を用意する。** 変更に着手する前に、[github-issue-workflow](../github-issue-workflow/SKILL.md) に従い、同じ作業の既存 Issue を確認する。未登録の作業は、全体を追う親 Issue と、完了条件・成果物・依存関係を持つサブ Issue を用意する。小さな変更はサブ Issue を1件にまとめる。既存のサブ Issue が対象なら、その親子関係を使う。
2. **サブ Issue ごとに調査・実装・検証する。** 個別にレビューできる差分になるよう、サブ Issue ごとに作業ブランチを分ける。依存する場合は、先行するサブ Issue と着手条件を明記する。対象の Issue に書いた完了条件と、下記の作業に合う手順を使う。
3. **サブ Issue ごとに PR を提出する。** 一つの PR に一つのサブ Issue の差分を載せる。同じサブ Issue を扱うオープンな PR があれば、それを更新する。PR 本文に対象のサブ Issue、変更内容、実行した検証と結果、未確認の範囲を記載する。PR のベースは原則として既定ブランチとする。既定ブランチ向けの PR では本文の `Closes #子Issue番号` で対象のサブ Issue を紐付ける。別のブランチ向けの場合は対象のサブ Issue を本文に明記し、既定ブランチ向けに切り替える際に紐付けを確認する。PR を開いたら、対象のサブ Issue と差分が対応していることを確認する。親 Issue は全体の進捗と完了判定に使う。コミット・push 前にはリポジトリの Git のルールに従う。

## 作業に合わせた検証

依頼と制約から、合否を判定できる条件を決める。主目的に合う手順を選び、対象の入口から関係する処理とテストをたどる。

| 目的 | 手順 |
| --- | --- |
| 調査 | 値の生成・保持・参照をたどり、失敗がどこに波及するかを調べる。確認できた事実と仮説を報告する。 |
| バグ修正 | 可能なら現行コードで再現し、観測結果で原因を絞る。原因箇所を修正し、同じ入口と条件で再実行する。環境エラーは再現の証拠に含めない。 |
| 機能追加・変更 | 影響する利用者経路と合格条件を決め、実装後にその経路を通す。障害時の挙動が契約に含まれるなら、そこも確かめる。 |
| リファクタリング | 維持すべき公開契約を特定し、変更前後で同じ検証を通す。 |

既存の規約と依頼されたレビュー手順に従う。モジュール間の契約を変える場合は、受け渡すデータの型と各モジュールの責務を先に決める。関連箇所から確認範囲を広げ、テスト出力は失敗箇所と結果の要約を読む。既存の検証を優先し、再現や回帰検出に不足があれば補う。UI・API・スクリプトの実行経路に合う検証を選ぶときは [検証手順](references/verification.md) を読む。

結果は合格条件ごとに、実行した操作またはコマンド、観測結果、未確認の範囲を必要な分だけ示す。作業を引き継ぐ場合は、依頼と制約、確認済みの証拠、次の一手を残す。提出結果は、親 Issue、対象のサブ Issue、対応する PR の URL がたどれる形で示す。
