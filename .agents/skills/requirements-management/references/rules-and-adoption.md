# ルールの要件化と組織への導入

参照章は第 4 章、第 12〜16 章。

## 法令・標準・契約・社内ルールから要件を導く

1. 正本の名称、条項、版、適用期間、対象と地域を特定する。法令、契約、標準、社内規則、ガイドライン、手順書などの位置づけを確認する。適用・優先関係が不明な場合は、解釈案と原文の該当箇所を法務・業務などの担当につなぐ。
2. 条項ごとに、誰が、いつ・どの条件で、何を行う・行える・禁じられるかを整理する。例外、期限、承認、記録の保存、通知や報告の責任も必要に応じて特定する。
3. 義務・禁止は、業務手順、役割と権限、機能、データに割り当てる。承認や例外は判断条件と手順に、記録義務は生成する証拠・保存・閲覧に、説明義務は通知や利用者の対応経路に落とす。適合を確認するテスト、観察、監査項目を要件に結びつける。
4. 条項・解釈・社内要件・検証・証拠の参照を残す。改定時は、対象条項から、業務・システム・データ・運用・マニュアルや教育・契約への影響をたどる。

架空の社内条項「取り消した定期レポートの配信を停止し、処理結果を記録する」を例に、中止可能な役割、停止が効く時点、予約済みの配信、記録する操作者・時刻・結果を具体化する。要件に、権限外の操作、停止前後の予約配信、監査記録の確認を対応づける。停止の成立時点を条項から判断できなければ、解釈と影響を示して確認する。

## 社内文書を構造化する

| 文書 | どの要件の根拠にするか |
| --- | --- |
| 規則・規程 | 義務、禁止、権限、責任分担、適用範囲。 |
| ガイドライン | 推奨、判断基準、専門家への引き継ぎ条件。 |
| マニュアル・手順書 | 入出力、順序、担当、承認、例外、運用支援。 |
| チェックリスト | 検証や監査の条件、確認する証拠。 |
| FAQ・教育・様式 | 案内、理解の支援、入力項目や提出物。 |

文書 ID、条項 ID、版、所管部門、適用日、正本を明示し、義務・禁止・条件・例外・手順と参照先を識別できるようにする。入力や検索の用途があれば、AI が参照できる資料の範囲と優先順位も記録する。人が読み Git で管理する用途には Markdown を使える。法令文書の構造を扱うシステムや外部交換に必要な場合に、XML や Akoma Ntoso、抽出した要求の交換には ReqIF などを検討する。

## 組織に取り入れる

事業責任者は価値と優先度、利用者・現場は業務の妥当性、開発・運用は実現・検証・対応を確認する。適用する領域に応じて AI・データ、法務、セキュリティ、監査、調達の担当を加え、正本の管理、要求の判断、変更の決裁、検証結果の記録を誰が担うかを決める。

現状を調べ、既存の台帳や Issue に主要な要求の根拠、対応する要件、検証、変更理由を記録するところから試す。小規模な案件で、影響分析にかかる時間、要求起因の手戻り、現場の記録負担を確認し、様式・教育・ツール・調達基準へ反映する。

原典の成熟度は、属人型 → 文書化型 → 管理型 → モデル活用型 → AI 協働型の 5 段階。次の改善は、各領域で足りない能力から選ぶ。例えば、要求文書はあっても変更理由や影響先を追えない場合は、台帳と変更履歴の整備から着手する。AI による聞き取り補助は、成熟度にかかわらず小さく試せる。

委託や外部サービスを使う場合は、業務・技術双方の受入条件、責任分担、版変更や事故の通知、再検証、証跡、データや成果物の利用・返却・削除、サービス終了時の引き継ぎを確認する。AI を使う場合は、モデル・プロンプト・評価データ、ログ、更新履歴の管理責任と利用範囲も扱う。
